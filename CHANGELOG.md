# Changelog

## Unreleased

- Assistant, fixed after the release: it now searches the site's own index for every question and gives the model the result only when a smart home word asked for it or the best result scores at least 12 (`USEFUL_SCORE`); otherwise the model answers from general knowledge with no sources, in one streamed run. Before, a question without a smart home word left the choice to the model through a tool: 33 seconds of "Læser dit spørgsmål …", the whole answer at once and no source links, although the site has guides on the subject (measured on the live site). The tool route, `MAX_MODEL_RUNS` and the `reading` stage are gone, a follow-up is searched together with the question before it, and the build now warns (it does not stop: scores move with every new page, and the site builds itself daily) when a question measured off-topic scores 12 or more or an on-topic one scores less (`OFF_TOPIC`/`ON_TOPIC` in `scripts/lib/site-index/probes.mjs`).
- Tools, fixed after the release: `/api/elpris` answered 502 on the live site, because Energinet's dataset address answers 429 to the address a Worker shares with every other Worker (14 of 14 calls measured from Cloudflare). The Worker now asks Energinet's download address for the same rows first (200 in 15 of 15 calls) and keeps the dataset address as a reserve; both answer shapes are read, and when both fail the fault of the first is the one in the log. An answer that lacks one price area gives the source its minute of peace too, instead of a new call at once for the missing area. In the browser a call for prices now ends after 12 seconds, so the homepage card goes back to its text instead of staying empty; a device clock that is set right while the page is open is no longer corrected; and the wait for the next quarter is covered by a test. Energinet is still the only source.
- Tools, fixed after an independent review before release: a number typed with a thousands sign ("1.500", "1,500") is refused with a text that asks for 1500 instead of being read as 1.5; the cheapest run is compared with starting now in øre/kWh when a price is zero or negative (it said "169 % lower"); the lowest price of the day is marked low also when many hours share it; requests that arrive together cost one call to Energinet, and an isolate without the Cache API keeps its own copy and its minute of peace after a failure; the price area is guessed from longitude and latitude when Cloudflare reports a region code that is not one of the five known ones (two regions are to be merged in 2027); a device clock more than a quarter of an hour off is corrected from the answer's `Date` header, in the tool and on the homepage; the add-on text no longer says that the electricity tax depends on the grid company; the tool says which day the prices were fetched when that is not today.
- Tools, fixed after a follow-up review before release: a request that waited for the cache while another request's answer landed no longer asks Energinet a second time; an answer from Energinet that stops before the current quarter is not kept and never replaces a copy that still holds the price of now; the call to Energinet ends after 8 seconds even if `fetch` does not react, and is handed to `waitUntil`, so it is finished and kept when the visitor who caused it leaves. The homepage card holds the room for its numbers and texts from the start (unseen stand-ins of the same length, with dashes for the numbers), so the page below it does not move when the prices arrive (measured at 320, 390 and 1440 px: the same height before and after); it compares the price level with today's hours (the hours it draws), hides the key for the cheapest run when no bar is marked, and goes back to its text if its code cannot be fetched. An answer from the browser's cache can no longer undo the correction of a device clock that is wrong. The privacy policy (section 2.4, both languages) now says that the first price area is guessed on the server from the region, or the approximate place, that Cloudflare reports, also for the homepage card.
- The homepage has a tools section: a card with the electricity price right now, today's hours as bars and the cheapest three hours in a row, beside a row per tool. The numbers come from the site's own `/api/elpris` and are fetched only when the card is near the screen; without JavaScript, or when the prices cannot be fetched, the card shows a text and a link instead of numbers. The electricity price tool and the homepage now fetch the prices through one module (`src/lib/tools/price-data.mjs`).

- The chat endpoint can deliver its answer as a stream. A request to `/api/chat` with `Accept: text/event-stream` gets Server-Sent Events: `status` (reading, searching, writing, revising), `sources` as soon as the site search has run, `delta` with the text, and `done` with the checked answer, which is the same body as the JSON response. Only the answer step is streamed, and no check is removed: input limits, rate limit, origin check, source filtering, YAML checks, timeouts and the fallback model apply as before, and a refusal is still a plain JSON error. If the primary model fails, the fallback model answers; text the reader has already seen is withdrawn first ("Rewriting the answer …"), and so is a finished draft that fails a check or a stream that closes before the model said it was done. If the fallback fails too, the reader gets an `error` event and the draft is removed, never a half answer shown as complete. A tool or tag name from the prompt is never shown, also when it arrives in several pieces or when the draft is cut off at the token limit in the middle of one, and a reader who stops during the search starts no model call. A stream in a shape the reader does not know gives no text and is logged as `unknown_primary_stream` or `unknown_fallback_stream`, also when it closes without `[DONE]`. A request without that `Accept` header gets the same JSON response as before, and `STREAMING_ENABLED` in `functions/lib/chat/limits.js` switches the stream off. The stream is tested against fakes only; the real model's stream must be checked on the live site with the `curl` command in `docs/assistent.md`.
- The assistant shows its answer while it is written. The widget asks for the stream: a status line says what happens ("Søger i guiderne …", "Skriver svar …"), source links appear before the text, and the text is drawn with the same safe renderer as a finished answer. "Stop" takes the place of "Send" while an answer is on its way, cancels the request and takes over keyboard focus; after a failure, focus lands on "Prøv igen". The view follows the text only while the reader stays at the writing position. Screen readers hear the status changes and the finished answer, not every word, and with reduced motion the text arrives in whole lines. A browser that cannot read a streamed body, or a stream that fails before the first text, gets the JSON response instead (one more request). Only finished answers are stored in `sessionStorage`.
